# 破产资产处置功能设计

日期: 2026-04-26

## 背景

当前项目中的破产处理仍是后台自动清算逻辑，核心行为集中在 `GameLoop.handleBankruptcy()`：

- 公司破产后立即进入自动清算
- 建筑会被系统自动卖给“现金最多的公司”
- 玩家公司也会被当作候选买家参与收购
- 玩家没有策略入口，也没有事件确认入口
- 挂单、合同、债务、股票与资产处置缺少统一的显式规则

这会带来两个问题：

- 规则不透明，玩家不知道为什么自己突然多了大量资产和维护成本
- 行为不可控，系统会替玩家接盘，甚至把玩家现金拖成负数

这次需求不是再给旧逻辑打补丁，而是把“破产资产处理”做成一个明确、可配置、可交互、可测试的独立功能。

## 目标

- 新增一个独立的破产资产处置系统，替代后台静默自动清算
- 为玩家提供两层控制：
  - 常驻策略设置
  - 真实事件发生时的手动确认入口
- 将破产处置明确拆分为：
  - 建筑与库存拍卖
  - 挂单取消与返还
  - 合同违约结算
  - 债务清偿
  - 股票退市
  - 重组冷却与新主体回场
- 明确禁止系统在未告知玩家的情况下替玩家自动接盘破产资产
- 让整个流程能被存档、回放、测试和扩展

## 非目标

- 本次不重做整个并购系统
- 本次不将正常并购与破产处置合并成同一套流程
- 本次不做复杂的法院破产优先级模拟或多层债权人法务模型
- 本次不保留旧的“后台自动转卖给现金最多的公司”逻辑
- 本次不实现真实连续竞价撮合市场，采用离散事件式竞拍即可

## 已确认的产品决策

本设计基于以下已确认选择：

- 总体形态：`C`
  - 有常驻策略开关
  - 真发生破产时仍有手动确认入口
- 建筑和库存处理方式：`B`
  - 公开竞拍，玩家和 AI 一起出价
- 债务和股票处理方式：`A`
  - 先还债，再退市重组
- 挂单和合同处理方式：`C`
  - 公开市场挂单立即取消并结算
  - 长期合同按违约规则单独处理

## 方案比较

### 方案 A: 轻量补丁型

在现有 `GameLoop` 破产逻辑外再包一层玩家确认与资产拍卖。

优点:

- 改动小
- 上线快

缺点:

- 底层仍然是自动清算思路
- 正常并购、破产拍卖、后台清算状态容易继续缠在一起
- 后续扩展风险高

### 方案 B: 独立破产处置系统

新增 `BankruptcyResolution` 模块，统一管理破产冻结、资产竞拍、债务清偿、退市和重组。

优点:

- 规则边界清楚
- 可以彻底停止后台替玩家决策
- 容易加策略开关、事件面板、存档状态和回归测试

缺点:

- 工作量高于补丁型

### 方案 C: 并购系统并入型

把破产处置直接揉进 `AcquisitionSystem` 和 `OwnershipControl`。

优点:

- 金融相关逻辑集中

缺点:

- 正常并购与破产清算语义不同，会混淆
- 容易把“主动收购”和“被动清算”写成同一套复杂分支

### 结论

采用方案 B。

破产资产处置是一个独立玩法流程，不应继续依附在 `GameLoop` 的后台清算分支中。

## 功能概览

### 两层入口

系统新增两个入口：

- 常驻策略入口
  - 玩家在设置中定义自己的默认参与方式
- 事件处理入口
  - 某家公司真的破产时，生成一个独立的破产处置事件，玩家进入事件面板决策

### 核心原则

- 系统不再静默替玩家接盘
- 玩家只有在主动出价或启用自动参与策略时才会进入竞拍
- 真正成交前必须有明确的事件上下文和金额信息
- 拍卖得到的是“干净资产”，不会继承旧挂单和旧合同
- 债务清偿和股票退市总在资产拍卖后统一结算
- 所有破产处置时间统一以“天”为单位推进和展示，不再出现小时制倒计时

## 用户体验设计

### 常驻策略入口

位置建议：

- `设置 -> 金融/风险`
  或
- `设置 -> 破产资产处理`

提供以下策略项：

- `自动参与`
  - 系统可按预设预算生成预出价
  - 真到成交前仍保留事件确认
- `只提示`
  - 发生破产时只弹事件，不自动下场
- `永不参与`
  - 玩家完全不参与竞拍，只查看结果

附加配置：

- `单次破产事件最高预算`
- `单个资产最高预算`
- `是否自动关注同行业资产`

### 事件入口

某公司破产后，系统生成一条 `破产处置事件`，并同时出现在：

- 通知中心
- 新闻/事件流
- 金融页或新增的破产市场入口

玩家点击后进入 `破产处置面板`。

### 手动确认语义

- 玩家手动提交的正式出价，提交即视为确认，不再二次确认
- `自动参与` 策略只会生成 `预出价`，不会直接扣款成交
- 若 `预出价` 在拍卖截止时成为有效最高价，系统进入资产级的 `待确认成交` 子状态，并展示：
  - 成交资产
  - 最终支付金额
  - 对玩家当前现金与预算上限的影响
- 玩家必须在确认窗口内手动确认该笔 `预出价` 才会真正成交
- 若玩家超时未确认，则该笔 `预出价` 自动作废，资产顺延给下一笔有效出价；若不存在下一笔有效出价，则按流拍处理
- 手动正式出价一旦提交不可撤销，只能等待被更高出价覆盖或拍卖结束
- `待确认成交` 仅是资产级临时状态，不新增公司级主状态机分支

### 破产处置面板结构

面板分为四块：

- `事件摘要`
  - 公司名
  - 破产原因
  - 总债务
  - 待拍卖资产数
  - 股票状态
  - 剩余处置时间
- `资产拍卖`
  - 分页展示 `建筑` 与 `库存`
  - 显示估值、当前最高价、剩余时间、竞拍人数、玩家出价
- `风险结算`
  - 展示拍卖所得如何分配
  - 展示债务清偿顺序
  - 展示退市与股东残值结果
- `处置结果`
  - 显示玩家拍得了什么
  - 花了多少钱
  - 原公司是否进入重组冷却

## 系统设计

### 核心模块

新增独立模块，例如：

- `src/core/finance/BankruptcyResolution.ts`

职责：

- 管理破产事件状态机
- 冻结公司经营状态
- 管理拍卖资产列表和竞拍状态
- 执行挂单取消、合同违约、债务清偿、退市与重组
- 提供 UI 所需查询接口

`GameLoop` 只保留“检测公司破产并创建破产事件”的职责，不再直接做资产自动转卖。

### 状态机

破产公司状态按以下顺序流转：

- `active`
- `bankruptcy_frozen`
- `auction_open`
- `settlement_in_progress`
- `delisted`
- `restructure_cooldown`
- `restructured`

说明：

- `bankruptcy_frozen`
  - 公司停止正常经营
  - 停牌
  - 停止继续走正常扩张与自动收购逻辑
- `auction_open`
  - 建筑和库存公开竞拍
- `settlement_in_progress`
  - 计算违约、清偿债务、结算股东残值
- `delisted`
  - 原股票退出市场
- `restructure_cooldown`
  - 处于待重组冷却期，不立即复活
- `restructured`
  - 作为新主体重新回场

### 触发条件

保留现有破产判定思路，但改成：

- 一旦满足破产条件
- 不再调用后台自动清算
- 改为创建 `BankruptcyEvent`
- 进入 `bankruptcy_frozen`

### 时间单位约束

- 所有破产流程的剩余时间、拍卖轮次、确认窗口、重组冷却统一使用游戏“天”推进
- `createdTick`、`expiresTick`、`auctionEndTick` 等字段在实现上仍可复用现有 tick，但语义必须映射到“第几天结束”而不是“第几小时”
- UI 文案统一显示 `剩余 X 天`、`第 X 天结算`、`冷却 X 天`，不允许再出现小时单位

## 资产处置规则

### 建筑

- 建筑进入公开竞拍
- 默认按单栋拍卖
- 玩家和 AI 可共同出价
- 玩家只有主动出价或启用自动参与策略时才参与
- 流拍时：
  - 先进入一次折价重拍
  - 再流拍则按清算残值销毁

### 库存

- 库存进入公开竞拍
- 默认按“同商品打包”拍卖，避免碎片化
- 流拍后直接按清算残值处理，不强制分配给任何公司

### 成交资产的语义

拍卖得到的是“干净资产”：

- 不继承旧挂单
- 不继承旧合同
- 不继承旧债务
- 不继承旧股权结构

## 挂单与合同规则

### 公开市场挂单

在 `bankruptcy_frozen` 阶段立即处理：

- 买单取消，返还冻结资金
- 卖单取消，返还剩余库存

这样可以确保：

- 竞拍资产不会同时被市场挂单占用
- 玩家拍得资产后不会继承旧订单状态

### 长期合同

长期合同不进入拍卖继承链路，而是按违约规则单独结算：

- 合同终止
- 按合同违约条款计算赔付
- 赔付款项进入破产清偿流程中的优先费用层

## 债务、股票与清偿规则

### 债务清偿顺序

拍卖所得进入一个 `破产财产池`，按顺序分配：

1. 处置费用与合同违约赔付
2. 银行和明确负债
3. 若有剩余，再按股权比例向股东分配残值

### 股票处理

- 公司一旦进入处置流程，股票停牌
- 资产拍卖和债务清偿完成后，原股票退市
- 原有股东结构清空
- 若清偿后没有剩余，股东残值为 0
- 若清偿后有剩余，按持股比例分配残值

### 重组

公司不会在退市后立刻原地复活，而是进入 `restructure_cooldown`：

- 冷却结束后，系统才允许其作为新主体回场
- 新主体获得新现金和新初始建筑
- 不继承旧债务
- 不继承旧股东结构
- 不继承旧破产资产

## AI 参与规则

### AI 出价

AI 可以参与公开竞拍，但必须满足：

- 预算充足
- 出价受现金上限约束
- 不允许无限透支抢拍

### 玩家保护规则

新增硬性规则：

- 所有后台自动资产接盘逻辑都不得把玩家公司作为隐式候选
- 玩家参与只能通过：
  - 主动出价
  - 自动参与策略

## 数据模型

建议新增以下数据结构：

- `BankruptcyEvent`
  - `id`
  - `companyId`
  - `status`
  - `createdTick`
  - `expiresTick`
  - `reason`
  - `auctionAssetIds`
  - `debtSnapshot`
  - `delisted`
- `AuctionAsset`
  - `eventId`
  - `assetType`
  - `assetId` 或 `goodsId`
  - `quantity`
  - `reservePrice`
  - `currentHighestBid`
  - `currentHighestBidderId`
  - `bidCount`
  - `auctionEndTick`
  - `state`
- `BankruptcyStrategySettings`
  - `mode`
  - `eventBudgetCap`
  - `assetBudgetCap`
  - `autoTrackSameIndustry`

## 存档要求

以下状态必须进入存档：

- 进行中的破产事件
- 每个拍卖资产的当前最高价
- 当前最高出价者
- 剩余时间
- 玩家已提交但未结算的出价
- 退市/清偿/冷却状态
- 玩家的破产参与策略设置

这样才能确保：

- 存档后继续竞拍不会丢状态
- 读档后不会重复结算或漏结算

## 边界情况

### 多家公司同日破产

- 每家公司生成独立事件
- 不共享资产池
- 不共享债务池

### 资产无人竞拍

- 建筑：折价重拍一次，再流拍则销毁
- 库存：直接按残值清算
- 不能再退回旧的“系统自动分配给现金最多的公司”

### 清偿不足

- 允许债务无法完全偿还
- 此时股东残值直接为 0
- 公司仍按流程退市

### 玩家未打开事件面板

- 事件仍按天数正常推进，不会因为玩家未打开面板而暂停全局时间
- 是否自动生成 `预出价` 由策略层决定
- 若玩家策略为 `只提示` 或 `永不参与`，则未操作等同于放弃本次竞拍
- 若玩家策略为 `自动参与`，则仅允许 `预出价` 继续竞争；进入 `待确认成交` 后仍需玩家在确认窗口内手动确认，否则自动作废
- 不会因为玩家没打开面板而替玩家成交

### 竞拍中存档/读档

- 读档后必须回到相同拍卖状态
- 不允许重复触发挂单取消、合同违约和债务清偿

## 测试方案

必须先补测试，再做实现。

### 单元测试

- 破产事件状态机从 `bankruptcy_frozen` 到 `delisted` 的流转正确
- 挂单取消后，冻结资金和库存返还正确
- 合同违约赔付进入正确清偿层级
- 拍卖所得按指定顺序清偿
- 清偿后股东残值计算正确
- 退市后股东结构清空

### 集成测试

- AI 破产后玩家在未出价的情况下不会被动接盘资产
- 玩家竞拍成功后只拿到拍卖资产，不继承旧债务
- 多家公司同日破产时事件与资产不串账
- 流拍资产按预期进入折价重拍或残值清算
- 长模拟中玩家不会因后台被动接盘而在第二年八九月被拖成负现金

### UI 测试

- `自动参与 / 只提示 / 永不参与` 三种策略行为正确
- 破产处置面板正确展示建筑、库存、债务与退市结果
- 玩家出价、`预出价` 确认、预算超限提示正确

### 存档测试

- 破产事件中途存档再读取后，拍卖状态完全恢复
- 读档后不会重复执行挂单取消和债务清偿

## 风险与缓解

### 风险 1: 破产逻辑仍残留在 `GameLoop`

如果新模块已上线，但旧的后台自动清算分支还在执行，玩家仍可能被隐式接盘。

缓解：

- `GameLoop` 只负责创建破产事件
- 旧的自动建筑转卖逻辑完全移除或封存

### 风险 2: 拍卖资产和市场挂单冲突

如果破产资产在拍卖时仍挂在公开市场，会出现双重出售。

缓解：

- 进入 `bankruptcy_frozen` 时先统一取消挂单

### 风险 3: 拍卖规模过大导致 UI 过载

单个破产公司可能有大量建筑和库存。

缓解：

- 建筑按单栋展示，但支持分页
- 库存按商品聚合为打包资产
- 面板只默认展示高价值资产，次级资产可折叠

### 风险 4: 玩家预算策略与事件确认冲突

如果同时有“自动参与”和“手动确认”，容易出现谁说了算不明确。

缓解：

- 策略层只负责“是否自动生成预出价”
- 真正成交前仍由事件层展示结果与支出信息

## 实施顺序

1. 抽离 `GameLoop` 中的后台自动破产清算行为
2. 新增 `BankruptcyResolution` 状态机与数据模型
3. 实现挂单取消、合同违约、债务清偿、退市流程
4. 实现建筑和库存公开竞拍
5. 新增玩家策略设置与事件面板
6. 补齐存档持久化
7. 跑破产回归、长模拟回归和构建验证

## 验收标准

- 玩家不会再被系统静默替代参与破产资产收购
- 破产资产以公开竞拍方式处置，玩家和 AI 可共同出价
- 挂单立即取消并正确返还，长期合同按违约规则单独处理
- 拍卖所得按既定顺序清偿债务，原股票退市
- 公司不会立即原地复活，而是进入重组冷却后以新主体回场
- 破产处置过程可存档、可恢复、可测试
