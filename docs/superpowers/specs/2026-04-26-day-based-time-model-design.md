# 天制时间模型重构设计

日期: 2026-04-26

## 背景

当前项目将游戏时间建模为 `1 tick = 1小时`，并在大量系统中默认使用 `24 tick = 1天`：

- `GameWorld` 中的日期格式包含小时字段
- `GameLoop` 中的 GDP、零售、服务、分销、期货、品牌、新闻等节奏依赖 `24`
- 生产、运营成本、库存缓冲、AI 采购和 AI 销售大量使用 `* 24` 或 `/ 24` 做日尺度换算
- UI 中的金融、市场、统计、存档、建造等页面直接把 tick 翻译成“小时/天”
- 多个系统直接写死 `24`，而不是通过统一时间常量表达语义

这意味着“小时制”已经不是单个常量，而是贯穿核心模拟、事件调度和展示层的基础假设。

本次需求不是只把文本里的“小时”改成“天”，而是将整个游戏的最小时间单位改为“天”，并让所有系统围绕天制运行。

## 目标

- 统一时间模型为 `1 tick = 1天`
- 将所有按小时推进、按天汇总的逻辑改成原生按天推进
- 移除或收敛核心代码中的 `24` 小时换算常量，统一通过时间语义常量表达
- 让生产、运营成本、市场、AI、金融、新闻、统计和 UI 都围绕天制运行
- 为旧小时制存档提供明确的迁移路径，避免无提示地读出错误时间

## 非目标

- 本次不重新设计经济系统的整体平衡目标，只做时间尺度重标定
- 本次不保留“小时制”和“天制”长期并存的双时间模型
- 本次不追求所有历史图表粒度完全不变，允许在天制下改为日聚合
- 本次不补齐当前本就未持久化的所有运行态系统，只处理现有存档结构和可安全扩展的迁移字段

## 方案比较

### 方案 A: 表面天制

仅修改日期展示、文案和部分图表，让 UI 看起来按天展示，但底层仍保持 `1 tick = 1小时`。

优点:

- 改动小
- 现有经济平衡几乎不变

缺点:

- 底层仍然是小时制，不符合需求
- 后续维护时会继续出现“显示是天，逻辑是小时”的分裂

### 方案 B: 彻底天制

统一将底层时间模型切换为 `1 tick = 1天`，所有核心系统都改成按天推进。

优点:

- 最符合需求，模型清晰
- 后续维护只需要理解一种时间语义
- 可以清理大量隐式的小时换算逻辑

缺点:

- 改动范围大
- 需要同步重标定经济、AI、统计和测试

### 方案 C: 彻底天制加过渡兼容

核心采用方案 B，同时为旧小时制存档和少量旧接口增加最小迁移层。

优点:

- 最终模型仍然干净
- 老存档和遗留数据迁移更平滑

缺点:

- 短期内需要维护一层迁移逻辑

### 结论

采用方案 C。

核心系统改为彻底天制，但在存档加载和少量旧数据入口上保留最小兼容，避免把迁移负担转嫁给玩家。

## 设计概览

### 核心原则

以后项目中的时间语义统一为：

- `1 tick = 1天`
- 所有“每日结算”变成“每 tick 结算”
- 所有“每月结算”使用 `30 tick`
- 所有“每年结算”使用 `360 tick`
- 所有时间相关代码优先使用统一常量，而不是硬编码 `24`

### 基础时间常量

时间常量调整为：

- `TICKS_PER_DAY = 1`
- `TICKS_PER_MONTH = 30`
- `TICKS_PER_YEAR = 360`

如果某些系统仍需要更明确的表达，应新增语义常量而不是继续写字面值，例如：

- `DAYS_PER_MONTH = 30`
- `MONTHS_PER_YEAR = 12`

### 日期模型

`tickToDate` 与 `formatGameDate` 改为纯天制输出：

- `tickToDate(tick)` 返回 `year / month / day`
- 不再返回 `hour`
- `formatGameDate(tick)` 改为 `第X年 X月X日`

所有 UI 和日志如果要展示时间，都必须使用新的日期结构，而不是继续拼接 `hour:00`。

## 生产与经济重标定

### 生产节奏

当前大量生产逻辑采用“每 tick 处理一天的 1/24，再在别处乘回 24”的方式。重构后改为：

- 建筑每 tick 直接产出 1 天产量
- 建筑每 tick 直接消耗 1 天投入
- 自动补料与安全库存直接按日需求和目标库存天数计算
- `calculateTheoreticalOutput`、`calculateDailyConsumption` 等 helper 保持“日产量/日消耗”语义，但不再依赖 `* 24`

这意味着：

- 现在的“日产量”会成为“每 tick 产量”
- 当前所有 `outputPerTick * 24`、`inputPerTick * 24` 需要改为统一使用 `TICKS_PER_DAY`
- 任何“7 天缓冲”“30 天库存”等逻辑改为直接基于天数，不再先换算小时

### 运营成本

当前运营成本是按“日成本 / 24”在每个小时 tick 扣减。重构后改为：

- 每个 tick 直接扣 1 天维护成本
- 人力、能耗等统计负担也按天记账
- 贷款月供、利息、附属设施维护等时间成本统一以天制推进

`OperatingCosts` 中现有的 `DEFAULT_TICKS_PER_DAY = 24` 将改为读取统一时间常量。

### 市场、消费与库存

以下系统统一改成天然日尺度：

- `DemandCurve`
- `ConsumerMarket`
- `RetailSystem`
- `ServiceConsumption`
- `InventoryDecay`
- `DistributionChannels`
- `SupplyContracts`
- `FuturesMarket`

改造规则：

- 之前按小时累计、按天汇总的需求和销售，改为每 tick 直接结算当日结果
- 库存保鲜期、账期、运输提前期、合同周期继续以“天”为业务单位，但不再乘以 `24`
- 零售、服务和成交统计中的“最近 24 tick”窗口改成真实的日窗口，例如最近 30 天、最近 60 天或明确的月度窗口

### GDP 与宏观统计

`GameLoop` 当前使用最近 `24 tick` 的成交与终端收入计算“日 GDP”，再年化。天制后改为：

- 每个 tick 直接代表 1 天经济活动
- `recentRetailRevenue`、`recentServiceRevenue` 等小时缓存改为日窗口缓存
- `updateGDP()` 直接基于最近 N 天数据或最近 1 天数据计算，再平滑年化
- 年化系数由 `365` 收敛为明确的游戏年长度 `360`

这样 GDP 仍保留“年化值”概念，但不会继续混用真实日历和旧小时制。

## AI 与系统节奏重构

### 核心要求

AI 与定时系统不能简单把 `24` 替换成 `1`。所有定时逻辑都必须重新映射到“按天推进”的新世界。

### AI 决策频率

当前 AI 决策、自动挂单、调价、附属建筑管理、紧急建造等节奏混合使用 `6 / 12 / 24 / 48 / 96 / 200` tick，这些原本分别对应数小时到数天。

重构后应按业务语义重新定义，例如：

- 每日执行
- 每 3 天执行
- 每 7 天执行
- 每 15 天执行
- 每月执行

具体原则：

- 与市场流动性和价格响应强相关的逻辑保持高频，但以“每日”或“每数日”表达
- 建造、产业规划、附属设施管理等中低频逻辑改为每周或每月
- 任何注释和常量名都应同步反映新的天制语义

### 库存天数与采购判断

当前 AI 大量通过 `demand / 24`、`output * 24` 计算库存覆盖天数。重构后改为：

- 库存天数 = 当前库存 / 日需求
- 日需求、日产出统一来自天制 helper
- 订单待交付天数、在途库存天数、挂单覆盖天数都直接按天计算

这样 AI 的“缺货”“过剩”“紧急采购”判断才能继续成立。

### 事件与周期

以下事件系统统一改成按天/月/年语义调度：

- 季节
- 新闻生成
- 月报统计
- 品牌冷却
- 商业周期
- 股票市场日更/周期更新
- 期货月合约创建和到期

所有原先依赖小时字段的代码要改为读取新的 `tickToDate` 结果，或者直接使用统一时间常量推导周期位置。

## UI 与展示层调整

### 日期和相对时间

所有展示“小时/天”的组件统一改成天制语义，包括但不限于：

- Dashboard
- Finance
- Market
- Statistics
- SaveLoadPanel
- Research
- Contracts
- Construction
- Achievement

改造规则：

- 去掉小时显示
- “小于 24 tick 显示小时”的逻辑改为直接显示天
- 所有 `Day X`、`近100小时`、`24h` 等文本改成真实天制口径

### 图表与聚合

当前部分图表同时存在“逐 tick 曲线”和“按天聚合 K 线”。天制后：

- 逐 tick 曲线直接等价于逐日曲线
- 现有日 K 线可以保留为更高层级聚合，例如周线或月线，也可以继续按日展示但需避免重复语义
- 所有使用 `tickToDate(...).hour` 的标签都要移除

### 帮助文案与 LLM 提示

以下用户可见说明也必须同步修正：

- Help/Tutorial 文案
- LLM prompt 中的“快进一天 = 24 tick”
- 任何描述“24 小时”“半天”“每小时”的配置说明

不能出现逻辑已改成天制，但引导文案仍让用户以小时理解的情况。

## 存档迁移与版本兼容

### 存档版本

为这次重构增加显式时间模型标记。建议：

- 提升存档版本号
- 在 `SaveData.metadata` 或 `SerializedWorld` 中新增时间模型字段，例如 `timeModel: 'hour' | 'day'`

新存档只写入 `day`。

### 旧存档迁移

加载旧小时制存档时执行以下迁移：

- `currentTick` 从旧小时 tick 折算为天 tick
- `metadata.playTime` 若用于展示，也同步折算到天制
- 若后续持久化结构中存在剩余时间、到期时间、账期、建造结束时间等 tick 字段，应统一按“向上取整到天且最少 1 天”的规则迁移

当前 `SaveManager` 保存的数据主要包括：

- `currentTick`
- 商品供需与价格
- 建筑状态
- 公司库存和现金

因此第一阶段迁移重点是：

- 正确迁移 `currentTick`
- 正确标记新旧时间模型
- 保证老存档加载后日期显示与游戏推进都进入天制

### 兼容边界

当前并非所有运行态系统都进入存档，因此本次不额外补齐所有未保存状态，只保证：

- 旧存档不会因时间模型变化直接损坏
- 玩家加载后进入的是明确的天制世界
- 不隐式保留小时制运行逻辑

## 测试方案

必须先补失败测试，再改实现。

### 时间基础测试

- `TICKS_PER_DAY / TICKS_PER_MONTH / TICKS_PER_YEAR` 符合天制定义
- `tickToDate` 在天制下正确换算年/月/日
- `formatGameDate` 不再包含小时
- 相对时间格式在任意 tick 下只输出天、月、年语义

### 生产与成本测试

- 建筑理论产出在天制下仍返回正确日产量
- 建筑日消耗与自动补料缓冲按天计算
- 运营成本每 tick 扣减 1 天成本，不再是 1/24 天
- 库存损耗和保鲜期判断基于真实天数

### AI 与调度测试

- AI 库存天数计算在天制下仍正确
- 自动挂单、采购、调价等节奏按新的日/周/月规则触发
- 原本“每日执行”的逻辑现在每 tick 执行 1 次
- 原本“每月执行”的逻辑在 `30 tick` 语义下仍准确触发

### 主循环与统计测试

- `GameLoop` 中的日/月事件触发频率符合新时间模型
- GDP、零售、服务、交易窗口不再依赖小时缓存
- 新闻、月度统计、期货月合约和季节判断在天制下仍正确

### 存档迁移测试

- 新存档能写入天制标记
- 旧小时制存档加载后 `currentTick` 被正确折算
- 迁移后日期展示与推进节奏是天制

### 回归验证

- 运行现有经济、财务、市场、统计、存档相关测试
- 运行一次 `npm run build`
- 如果某些组件测试依赖旧小时文本，需同步更新断言

## 风险与缓解

### 风险 1: 隐式 `24` 遗漏

如果只改常量，仍然会有大量逻辑保留旧小时制语义。

缓解:

- 全局搜索 `24`、`/ 24`、`* 24`、`hour`、`24h`
- 优先把核心模块中的字面值替换成统一时间常量或语义 helper
- 为关键模块补充天制测试防止回退

### 风险 2: AI 节奏失真

如果直接把 `24` 改成 `1`，部分 AI 会从“每小时检查”变成“每天检查”，或反过来触发过于频繁。

缓解:

- 所有 AI 频率按业务意义重新映射
- 将高频、中频、低频任务分层整理，明确新的日/周/月节奏

### 风险 3: 图表和统计口径不一致

若核心已经改成天制，但图表仍按“逐 tick = 逐小时”解释，会导致趋势图和标签失真。

缓解:

- 所有图表统一把 tick 解释为日
- 明确每张图是日线、周线还是月线

### 风险 4: 旧存档无提示迁移

如果老存档被静默折算，玩家可能误以为游戏时间丢失或跳变。

缓解:

- 存档元数据中加入时间模型信息
- 在加载旧存档时输出明确的迁移日志或用户提示

## 实施顺序

1. 建立统一时间常量和日期 helper，确定 `1 tick = 1天`
2. 为时间基础函数和存档迁移补失败测试
3. 重构 `GameWorld`、`GameLoop`、存档和通用格式化函数
4. 重构生产、运营成本、库存、零售、服务和市场的天制折算
5. 重构 AI 的库存天数计算与周期调度
6. 迁移 UI 页面、图表、帮助文案和 LLM 提示
7. 跑相关测试与构建，修复回归

## 验收标准

- 项目统一使用 `1 tick = 1天`
- 游戏日期、时间格式和相对时间展示不再出现小时字段
- 生产、运营成本、库存、市场、AI、金融和新闻都按天制运行
- 核心代码中不再依赖隐式 `24 tick = 1天` 作为事实前提
- 旧小时制存档可以通过明确迁移进入天制世界
- 相关测试和构建验证通过
