# 生产控制开关与手动产量设计

日期: 2026-04-25

## 背景

当前建筑效率同时承担了两类职责:

- AI 会根据盈利情况自动上调或下调效率
- 生产系统会在过剩供给时自动压产，并在市场恢复后逐步恢复

这导致用户无法稳定地手动锁定建筑产量，尤其是在玩家已控股或完全控制的 AI 公司中，建筑会继续被自动系统覆盖。需求是为建筑增加正式的“自动调整产量 / 手动调整产量”控制能力，并覆盖玩家公司建筑与所有玩家拥有经营控制权的受控公司建筑。

## 目标

- 为单栋建筑提供 `自动` / `手动` 两种产量控制模式
- 在 `手动` 模式下，用滑条稳定锁定建筑效率，不再被自动调产逻辑覆盖
- 支持玩家公司建筑和所有玩家拥有 `influence_strategy` 权限的受控公司建筑
- 保持现有多配方建筑、启停建筑、升级等流程兼容
- 保持旧存档兼容，新字段有明确默认值

## 非目标

- 本次不做“整家公司批量调产”界面
- 本次不重做 AI 的配方选择逻辑
- 本次不改变现有效率的经济含义，只增加控制方式

## 方案比较

### 方案 A: 世界状态正式建模

在 `GameWorld.buildings` 中新增生产控制模式和手动效率目标。自动系统遇到手动模式时跳过该建筑。

优点:

- 状态与世界数据、读档、运行时逻辑一致
- 玩家建筑和受控公司建筑可以走统一路径
- 最容易保证“手动就是不会被覆盖”

缺点:

- 需要同时修改数据结构、自动逻辑、store、UI 和测试

### 方案 B: 仅在 UI/store 保存手动值

UI 或 store 保存拉条值，每 tick 再把效率写回去。

优点:

- 实现快

缺点:

- 状态不属于世界模型，容易和自动系统打架
- 读档和跨系统一致性差

### 方案 C: 只屏蔽 AI 调产

只让 AI 停止改效率，保留过剩供给压产。

优点:

- 改动最少

缺点:

- “手动”仍然可能被市场系统改掉，语义不成立

### 结论

采用方案 A。

## 设计概览

### 数据模型

在 `src/core/world/GameWorld.ts` 的 `BuildingsSystem` 中新增两组建筑级状态:

- `productionControlModes: Uint8Array`
  - `0 = auto`
  - `1 = manual`
- `manualEfficiencyTargets: Float32Array`
  - 保存建筑的手动目标效率
  - 数值范围与现有系统一致，为 `0.3 - 1.5`

默认规则:

- 新建建筑默认 `auto`
- 老存档加载时，所有建筑默认 `auto`
- 老存档的 `manualEfficiencyTargets` 默认回填为当前效率；若当前效率无效则回填 `1.0`

### 核心行为

#### 自动模式

- AI 调产逻辑保持原样
- 过剩供给压产与恢复逻辑保持原样
- 建筑效率继续由系统动态变化

#### 手动模式

- 建筑效率由 `manualEfficiencyTargets[buildingId]` 决定
- AI 调产逻辑不得修改该建筑效率
- 过剩供给压产与恢复逻辑不得修改该建筑效率
- 手动目标变化时立即生效

#### 模式切换

- 切到 `manual` 时:
  - 若用户未修改滑条，手动目标初始化为当前效率
  - 建筑效率立即对齐到手动目标
- 切回 `auto` 时:
  - 不强制重置到 `1.0`
  - 当前效率原样保留，后续交回自动系统接管

## 权限与作用范围

建筑控制权限取决于建筑 owner:

- owner 为玩家公司时，允许修改
- owner 为非玩家公司时，只有玩家对该公司拥有 `influence_strategy` 权限才允许修改

这意味着以下建筑都支持该功能:

- 玩家自有建筑
- 玩家已控股并拥有经营影响权的公司建筑

没有权限时:

- UI 只读
- store/action 也必须拒绝写入，避免仅靠前端禁用造成越权修改

## UI 设计

控制入口落在 `src/ui/components/Production/BuildingDetailPanel.tsx`。

在现有效率信息区域下新增一块“产量控制”面板，包含:

- 当前控制模式标签
- 归属公司说明
- 若为受控公司建筑，显示“受控公司建筑”提示
- `自动调整产量` 开关
- `手动产量` 滑条

交互规则:

- 开关打开时表示 `auto`
  - 显示“当前由系统自动调节”
  - 滑条禁用
  - 继续展示当前实际效率
- 开关关闭时表示 `manual`
  - 滑条启用
  - 范围为 `30% - 150%`
  - 边拖边生效，不增加单独保存按钮
  - 同时显示当前效率与手动目标

错误与提示:

- 无权限时显示明确提示文本，不做无反馈失败
- 若世界状态不存在或建筑越界，不渲染控制区

## Store 与接口设计

在 `src/stores/gameStore.ts` 中新增面向 UI 的动作:

- `getBuildingProductionControl(buildingId)`
- `setBuildingProductionControlMode(buildingId, mode)`
- `setBuildingManualEfficiencyTarget(buildingId, target)`

这些动作负责:

- 校验建筑存在
- 读取 owner
- 校验玩家是否有对应控制权
- 规范化目标范围到 `0.3 - 1.5`
- 在切换到 `manual` 或更新目标时同步 `world.buildings.efficiencies[buildingId]`

## 自动系统修改点

至少需要拦截以下自动写效率入口:

- `src/core/ai/AIDecisionEngine.ts`
- `src/core/ai/AIOptimizer.ts`
- `src/core/production/ProductionEngine.ts`

统一规则:

- 写效率前先检查该建筑是否为 `manual`
- 若是 `manual`，直接跳过自动调节
- 若是 `auto`，保持现有逻辑

如代码中存在其他效率写入点，也必须统一遵守该规则，避免出现“部分系统尊重手动、部分系统不尊重”的分裂行为。

## 多配方建筑与所有权变化

### 多配方建筑

- `outputModeId` 的切换逻辑保持不变
- 生产控制模式只影响效率，不干涉当前产出配方

### 所有权变化

- 建筑在收购、资产转移后，控制模式和手动目标随建筑一起保留
- 但玩家是否还能继续修改，取决于新 owner 对应的控制权

## 测试方案

先补测试，再实现。

核心行为测试:

- `manual` 模式下，AI 调产不会覆盖效率
- `manual` 模式下，过剩供给压产不会覆盖效率
- `auto` 模式下，AI 调产仍能改变效率
- `auto` 模式下，过剩供给逻辑仍能改变效率

权限测试:

- 玩家自有建筑可以切换控制模式和修改手动目标
- 玩家对受控公司具有 `influence_strategy` 权限时可以修改
- 没有权限时，store/action 拒绝修改

兼容测试:

- 旧世界数据补默认值后，所有建筑默认为 `auto`
- 新建建筑默认 `auto`
- 多配方建筑在手动模式下仍可切换产出模式

UI 验证:

- 如果现有测试基础便于覆盖组件交互，则补充建筑详情面板在有权限和无权限时的显示测试
- 如果现有测试基础不适合组件级测试，则至少通过构建与手动验证确认界面状态正确

## 风险与缓解

### 风险 1: 效率写入点遗漏

若某些系统仍直接写 `world.buildings.efficiencies`，手动模式仍可能被覆盖。

缓解:

- 搜索并审计全部效率写入点
- 将“是否允许自动改效率”的判断集中成可复用逻辑
- 用测试覆盖 AI 与市场两条主路径

### 风险 2: 老存档字段缺失

新增数组字段后，旧档若不补默认值可能触发读取异常。

缓解:

- 在世界初始化/加载路径统一做字段补齐
- 回归测试覆盖旧数据默认化

### 风险 3: 权限只在 UI 层控制

如果只禁用 UI，不限制 store/action，仍可能被脚本或其他入口越权修改。

缓解:

- 在 store/action 层做最终权限检查

## 实施顺序

1. 为世界数据新增控制模式与手动目标字段，并补默认值
2. 为 store 增加读取与修改动作，并加入权限校验
3. 为 AI 调产与过剩供给调产增加手动模式拦截
4. 在建筑详情面板加入开关和滑条
5. 补齐并通过回归测试与构建验证

## 验收标准

- 玩家可在建筑详情中将建筑切换为自动或手动产量
- 手动模式下，效率稳定停留在用户指定值，不再被自动系统覆盖
- 该能力可用于玩家建筑和所有具备经营控制权的受控公司建筑
- 自动模式下，现有经济系统行为保持不变
- 旧存档不会因新增字段而损坏或改变建筑默认行为
